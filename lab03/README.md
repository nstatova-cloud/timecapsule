Почему доступных адресов не 256? Какие адреса подсети 10.X.0.0/24 занимает AWS и для чего? Сколько ещё подсетей /24 поместится в вашу VPC?

Потому что 5 адресов сразу резервируется AWS. Остается 251
10.0.1.0 Адрес самой сети
10.0.1.1 Маршрутизатор VPC, шлюз по умолчанию для подсети
10.0.1.2 DNS. Сам сервер DNS находится по адресу «начало VPC плюс два»
10.0.1.3 Зарезервирован AWS на будущее
10.0.1.255 Последний адрес: широковещания в VPC нет, но адрес занят

Является ли подсеть public-a сейчас публичной? Почему? 
Нет, для того чтобы она стала публичной, нужно чтобы таблица маршрутов содержала маршрут в Internet Gateway

Какой маршрут есть в обеих таблицах, хотя вы его не добавляли? Что он даёт? Куда уйдёт пакет из private-a, адресованный 8.8.8.8?
В обеих таблицах по умолчанию есть маршрут local. Он дает доступ адресам внутри AWS друг к другу через внутреннюю сеть AWS. При изначальной настройке в route table есть только маршрут local, 8.8.8.8 не принадлежит диапазону подсети, поэтому пакет никуда не уйдет.

Почему в db-sg источником указана группа web-sg, а не адрес веб-сервера или диапазон 10.X.0.0/16?
Это безопаснее и удобнее по нескольким причинам. Прежде всего задается доступ по роли сервера, а не адресу. Даже если сервер находится в той же VPC сети соединение не пройдет по local маршруту. Использование конкретного ip веб-сервера неудобно, посколько когда сервер будет пересоздан у него будет новый private ip, правило придется менять вручую, что неудобно 

Почему db-server не может скачать пакеты, хотя web-server это делает? Что нужно добавить в сеть, чтобы это стало возможно, и при этом db-server остался недоступным из интернета?
У db-server нет публичного ip и маршрута в интернет. Чтобь скачать пакеты и не быть доступным из интернета, нужно добавить NAT Gateway, через который будут инициироваться соединения наружу.

Доступ к базе теперь ограничивают три механизма: отсутствие публичного адреса и маршрута в Internet Gateway, Security Group db-sg и файл pg_hba.conf. Что делает каждый из них? Что произойдёт, если ошибиться только в одном?

1. У бд нет публичного адреса, соединения наружу проходят по NAT, после его удаления к db-server нет доступа из публичнгого интернета 

2. Security group дает ограничения в соединении внутри VPC. Соединение с сервером происходит только если security group разрешает

3. pg_hba.conf задает правила внутри бд. В файле прописаны правила для доступа к базе, к примеру требования пароля, и наличие конкретной роли.

Если ошибка произойдет только на одном уровне, сработает защита остальных уровней, остальные продолжат ограничивать доступ.

Что содержит образ? Какие данные из ЛР2 оказались на app-server без всякой установки? Где сейчас хранится база данных приложения?

Образ AMI содержит все содержание старого диска без всякой установки: nginx, php-fpm, laravel, код приложения, зависимости, локальная бд, данные старой базы. После запуска база приложения находится локально на app-server, на db-server перенесение происходит через pg_dump и psql

Почему Elastic IP нужен app-server, но не нужен bastion? Сколько стоит Elastic IP, пока сервер остановлен, и почему? Когда в следующих работах перед сервером появится балансировщик нагрузки, понадобится ли Elastic IP?

Elastic IP позволяет закрепить публичный адрес за app-server, который не нужно менять при его перезапуске. Поскольку app-server это пользовательская точка входа в приложение, наличие постоянного адреса будет удобно и изменение адреса не будет затрагивать всех пользователей. Bastion же использует только администратор, поэтому в этом случае допустимо изменение одной строки для одного человека. Пока сервер остановлен elastic ip стоит 0.005$. При наличии балансировщика нагрузки теряется надобность в elastic ip, потому что пользователь будет обращаться к load balancer.

Зачем для базы в отдельной сети нужен новый сильный пароль, если порт 5432 и так закрыт Security Group?
Security Group это только один слой защиты, если получен доступ к серверу, либо случайно разрешается больше исчточников, чем нужно, то ничего больше не ограничивает доступ к базе. Сильный пароль защищает учетную запись базы данных от таких ситуаций.

Почему с app-server имя находится, а с вашего компьютера нет? Что придётся изменить, если db-server пересоздадут с другим адресом?
db.timecapsule.internal создается внутри private hosted zone, которая привязанв к vpc внутри aws. Компьютер находится вне этой сети, поэтому доступа нет. Если сервер пересоздан с другим адресом нужно менять только db.timecapsule.internal, настрйки приложения не меняются.

Файлы, которые пользователи прикрепили к капсулам, переехали вместе с образом, а не вместе с базой. Где они лежат? Что с ними будет, если app-server удалить?
Эти файлы лежат в файловой системе, которая переходит вместе с образом сервера. Если app-server удалить удаляется и диск, поэтому данные пропадут.

1. Как проходит запрос пользователя от браузера до базы данных? Какие маршруты и фильтры он проходит?
Сначала браузер отправляет HTTP-запрос на публичный IP app-server. Запрос приходит в VPC через Internet Gateway, проходит NACL публичной подсети и web-sg, после чего его принимает nginx и приложение. Когда приложению нужны данные, оно через Route 53 узнаёт private IP db-server по имени db.timecapsule.internal. Затем app-server отправляет запрос на порт 5432 внутри VPC по маршруту 10.X.0.0/16 -> local. На стороне базы запрос проходит NACL, db-sg, pg_hba.conf и проверку логина и пароля PostgreSQL.

2. Злоумышленник знает приватный IP db-server. Что ему нужно получить, чтобы подключиться к базе?
Одного знания private IP базы недостаточно, потому что этот адрес недоступен напрямую из интернета. Злоумышленнику сначала нужно попасть внутрь VPC, например скомпрометировать app-server. Затем соединение должно быть разрешено db-sg, PostgreSQL должен разрешить его в pg_hba.conf, и после этого ещё нужны правильные имя пользователя и пароль базы.

3. Чем Временный NAT Gateway лучше тем, что не создаёт постоянных расходов и private subnet большую часть времени вообще не имеет выхода в интернет. Недостаток — его нужно вручную или скриптами создавать перед обновлениями и затем полностью удалять вместе с маршрутом и Elastic IP. 

4. Как изменится схема, если приложение должно пережить отказ eu-central-1a?
Сейчас приложение не переживёт отказ eu-central-1a, потому что и app-server, и db-server находятся в этой зоне. Для отказоустойчивости нужен второй экземпляр приложения в eu-central-1b и Load Balancer перед двумя серверами. Для базы нужна вторая реплика в private-b
. Также пользовательские файлы нужно вынести с локального диска одного app-server в общее отказоустойчивое хранилище.
